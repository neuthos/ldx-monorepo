# Customer Order Tax Classification Test Plan

## 1. Summary

### TL;DR

This plan is ready for implementation handoff with two non-product `PENDING` test prerequisites: supported maximum Customer Order/batch capacity and its SLA are undefined, and the current UI action that invokes direct Customer Order-to-Sales conversion is not evidenced. The highest-risk behaviors are the distinction between null and ordinary 0%, snapshot preservation when Product/Tax defaults later change, FE/BE parity for grouped percent and fixed-tax rounding across currencies, blank-versus-absent batch intent, copy provenance validation, and preventing Customer Order tax from leaking into Shipment while still propagating it exactly to direct and Shipment-originated Sales.

### Coverage and confidence

- BR/FR coverage: 17/17 (100%), based on explicit traceability to `PRD §1.2`, `PRD §2.1–2.2`, `PRD §3.1–3.5`, and `Scenario 01–10`. The source has no formal FR/BR IDs, so its identifiers are preserved rather than replaced.
- Test-plan confidence: 90% (estimated, not execution evidence).
- Confidence rubric: requirement traceability 40/40, BOUNDARIES evaluation 18/20, blast-radius/domain-effect coverage 18/20, test-level fit 9/10, repository evidence 5/10. Repository evidence is reduced because the configured graph exposes only an unrelated repository; backend evidence therefore came from narrow source/ADR inspection plus exact-literal scans of other addon roots rather than a complete runtime graph.
- Total test cases: 65 finalized + 2 PENDING.
- Why this is sufficient: every source requirement and acceptance criterion has concrete coverage across deterministic rules, persisted/API contracts, and six planned critical vertical journeys. The plan covers both direct and Shipment-mediated Sales artifacts rather than stopping at the Customer Order screen. The two remaining gaps are execution prerequisites, not missing product behavior; direct Sales is already finalized at Unit/Integration levels while its UI journey awaits an evidenced trigger.

### Healthy pyramid

- Target: Unit ~70%, Integration 15–20%, E2E 5–10%.
- Actual across all 67 planned rows, including two PENDING rows: Unit 46/68.7%, Integration 15/22.4%, E2E 6/9.0%. Among the 65 finalized rows only: Unit 46/70.8%, Integration 14/21.5%, E2E 5/7.7%.
- Assessment: risk-adjusted deviation. The calculation uses rows, not steps. Integration is 2.4 points above target because API-loaded FE intent, Odoo persistence/copy/batch behavior, the installed `ldx_ec` preview override, and Sales propagation require independently diagnosable contract tests. Six E2E rows are retained for interactive, Apply-to-All, copy, batch, Shipment-originated Sales, and PENDING foreign-currency direct-Sales journeys.

- The graph limitation means these paths are evidence-backed but not claimed as a complete backend blast radius outside `ldx_addons`. Implementation sessions must rerun current repository-prescribed impact analysis before editing.

### Assumptions, unknowns, and PENDING decisions

- The design spec is the product-intent source of truth; all `DEC-01–DEC-18` decisions remain `USER-APPROVED` and are not reopened by this plan.
- FE, BE, and E2E are valid, clean Git worktrees. BE and E2E match the design evidence revisions. FE advanced by one CI/unit-test commit from the design snapshot, but no Customer Order, batch, Tax selector, rounding, or Shipment-to-Sales feature files changed.
- `PENDING`: define the supported maximum interactive line count, maximum batch data-row count, measurement environment, and pass/fail latency/query thresholds before executing the maximum-capacity row.
- `PENDING`: identify the exact direct Customer Order-to-Sales UI action/state and add a stable hook before finalizing that E2E row; no current E2E POM or selector exposes the trigger.
- Execution prerequisite: supply an actual guest-role E2E fixture if guest UI coverage is required. Current E2E auth fixtures provide admin/write/read/approval variants but no guest; authorization remains finalized at Unit/Integration levels.
- Ownership note: choose which of the two existing Shipment POM families owns TAX-058 during E2E implementation. Reuse is required; this plan does not silently authorize a third POM.
- E2E execution prerequisite: configure the new journey suite with `test.describe.configure({ mode: 'serial' })`, run it with `--workers 1`, and, if it lives outside `tests/scenario/inventory-list`, create a one-worker `test-modules.json` module and exclude it from the five-worker general module through the repository's serialized coordinator.
- Final localized validation/error key identifiers and a named object-level role matrix are implementation/test-data inputs; behavior, bilingual presence, company scope, and existing-policy preservation are already fixed by the spec.
- Existing concurrent-edit and double-submit behavior is a non-goal; the feature adds no optimistic locking or idempotency contract. This plan tests feature-specific races without inventing a new conflict policy.
- Broader mobile, Safari, Firefox, and visual-regression matrices are omitted because the approved environment defines Desktop Chromium as the current gate. Accessibility is covered at component/semantic-control level where the new selectors and dialog are introduced.
- No application or test repository was modified, no test was executed, and no database, service, branch, commit, or index was changed while preparing this plan.

## 2. Data Preparation Summary

- Tax Master fixtures: in the current company, active ordinary percent taxes at 10%, 8%, and 0%; synthetic active fixed taxes at 3.000 and 3.333 per unit because the current seeded fixed record is archived; one active `is_tax_free = true` record; one archived ordinary record; one ordinary record in another company; one unsupported classification shape; and two eligible `default_tax_sale` records with distinct `write_date` values to prove deterministic newest-first resolution.
- Product Master fixtures: Product A with active 10% `rate_of_tax_id`, Product B with active 8%, Product C with ordinary 0%, Product D with no Product tax, Product E referencing an ineligible/archived tax, two Service Products, and duplicate Customer Order Service lines that share a Product but have different tax snapshots.
- Company/contract configurations: default Sales Tax set and unset, `rounding_method_sales` separately set to `rounding`, `round_up`, and `round_down`, plus a controlled later policy change for reread tests.
- Currency fixtures: JPY with precision 0, a foreign transaction currency with precision 2, and a configured nonstandard currency with precision 3. Use the exact canonical vectors V-01–V-14c from the design spec.
- Customer Order line values: quantities 0, 1, 1.5, 2, and 0.75; net unit prices 10,000, 5,000, 999, 10.05, 1.2345, 100.05, 100, and -999; distinct `price_cut` values proving tax uses the already-net `order_unit_price` only once.
- Existing-order states: editable draft with active tax, editable draft with null, line with ordinary 0%, line with archived snapshot, legacy pre-feature line with null, confirmed/locked order, cancelled order, reserved order, order with Shipment created, and an order whose Sales already exists.
- Copy fixtures: source order containing an active manual override different from Product/default, null, ordinary 0%, and archived snapshots; source/default changes while the copy form is open; inaccessible source order, mismatched source line/order, and mismatched Product identity.
- Batch files/patterns: a new pattern with `Tax Classification` and `Shipment Address`; an unchanged saved old pattern omitting both; new and existing-line rows with nonblank, blank, whitespace-only, absent, Japanese/multibyte, invalid, archived, tax-free, other-company, and transposed Tax/Address values; errors use backend 1-based data-row ordinals.
- Actors/sessions: authorized Customer Order editor, read-only/wrong-role user, unauthenticated user, expired session, same-company and another-company records, and a user lacking read access to the copy source. Execution prerequisite: provide an E2E guest credential/role fixture if guest UI coverage is selected; backend role/guest behavior uses transaction-local users meanwhile.
- Shipment/Sales fixtures: direct service conversion, service-only foreign-currency order, Customer Order-generated normal and partial/split Shipments, broken row-level source under validated Customer Order provenance, duplicate Service pseudo-lines, generic Shipment, EC Shipment with number only, and a Customer Order Shipment with header/validated relation provenance. Product F must have nonempty standard Odoo `taxes_id` while its Customer Order snapshot is null, proving converters send an explicit empty Sales tax relation. The direct-Sales FE trigger remains a table-level PENDING; choose one existing Shipment POM family for TAX-058 ownership before E2E implementation.
- Integration-failure controls: failed Tax/Product lookup, save validation error, batch invalid-row result, Shipment preview exception, Sales conversion exception, malformed or overbroad preview request, and retry after a failed read without altering form intent.
- UI/environment matrix: English and Japanese resources, Japanese/multibyte Tax names plus punctuation/emoji/RTL master-provided text, Desktop Chromium in `Asia/Tokyo` and `en-US`, wide and horizontally constrained desktop viewports, and slow-network simulation for lookup intent preservation.
- Reset/cleanup: use synthetic, uniquely prefixed records; restore company rounding/default tax and any archive mutation in `finally`. Backend/FE Integration data rolls back through transaction/savepoint/MSW fixtures. E2E currently has no proven Customer Order/Shipment/Sales cleanup fixture, so uniquely prefixed created records may remain in the shared preview database; the suite must still run serially with one worker and restore every global configuration it changes.
